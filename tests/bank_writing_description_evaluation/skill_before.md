# 银行专业写作

## 一、定位与边界
本 Skill 只承担银行综合材料的**文本写作与编辑**：需求分析、素材梳理、观点提炼、结构设计、起草、修改、润色、整合与审校。

- 默认直接在对话中交付完整、可复制的中文文稿。
- **不负责生成 DOCX、PDF 或其他文件**，不进行自动排版、导出、格式转换。
- **不调用脚本生成或改写正文、制作文档、排版或转换**。精确长度可用宿主已有工具或标准库只读计数，不执行正文、不安装组件、不生成文件。本技能包不包含脚本。
- DOCX 导出由本项目独立的 `docx` Skill 负责；按[DOCX 导出交接](#六docx-导出交接)处理授权与正文交接，不将文件生成纳入本技能。
- 不为展示流程而强制输出分析过程；能直接完成的任务直接交付。

## 二、写作总原则
1. **事实准确**：不编造业务数据、工作成绩、政策依据、客户案例、会议决议、审批结论或领导讲话。缺失的重要信息用〔待核实〕、〔待补充数据〕标记。
2. **口径一致**：严格区分期间、机构、统计范围、计量单位、同比/环比、计划/在办/已完成及个人/集体职责。状态或结果未知时标明待核，不改写为“正在、持续”等未经确认的状态。
3. **银行语境**：正式、务实、严谨、克制；体现经营管理、客户服务、风险防控、合规经营和执行落实的业务特点。
4. **内容为本**：有事实说事实，有问题说问题，有举措说路径；避免空泛表态、套话叠加和不必要的宏大修辞。
5. **尊重原稿**：润色和改写不得擅自改变原意、政策口径、事实状态和责任主体。
6. **保密审慎**：不扩散不必要的客户隐私、账号、交易及内部敏感信息；对无法核实的合规判断不作确定性结论。

## 执行环境约束与首步自检

1. 本技能主要面向云端 Linux 容器中的对话式文本写作，开发环境可为 macOS、Windows 或 Linux；不依赖平台特有路径、解释器、第三方包或办公软件。开始前确认任务要求和素材可访问；读取不全时说明实际范围，不声称已审阅全文。精确计数等可选工具须确认宿主已提供；本地检查不能代替未执行的云端验收。
2. 以实际读取本 `SKILL.md` 的路径确定 `<skill_dir>`；内部参考资料以该目录定位，Markdown 链接相对于所在文件解析。无法确认位置时停止依赖该资源的操作，不猜测目录或使用宿主路径掩码。
3. 涉及本地素材时，先由宿主确认任务工作目录，输入使用该目录及其子目录内的相对路径；不通过父目录、绝对数据路径或切换挂载绕过边界。内部资源可使用已确认的完整路径；不得将任务文件写入技能安装目录。
4. 本技能没有自检脚本。首次写作前逐项确认：任务类型与交付要求明确、必需素材可读、按需使用的参考资料可读；全部满足才开展依赖这些条件的写作。纯对话不涉及目录写入与下载交付，无需读写探针或文件自检命令。
5. 如需宿主工具读取素材，先确认工具确实可用且具有所需权限；缺失时报告限制，不安装组件或自行改用文档转换流程。文件制作属于独立能力，使用时另行检查其环境与任务目录读写条件。
6. 自检失败或无法确认时，停止依赖该条件的操作，说明具体缺失项；只有问题解决后才重新检查，不原样反复重试或降低要求。可以继续不依赖缺失素材的部分，并明确范围。
7. 自检通过不等于文稿合格。交付前仍按正文和参考资料审校事实、口径、逻辑及用户要求；输出可复制文本，不虚构产物路径或下载链接。
8. 长会话压缩后若约束不完整，重新读取真实 `SKILL.md`；保留已确认的任务目录和素材名称，不凭记忆重建路径。

## 三、标准写作流程
### 1. 理解任务与场景
判断写作类型（起草/提纲/续写/整合/改写/压缩/扩写/润色/审校）、文种、受众、场合、主旨、篇幅和语气。摘要、仿写或先摘要再仿写，按[三条任务路径](references/summary-and-imitation.md)执行；普通写作不增加这些流程。缺少非关键细节时采用稳妥默认值；只有关键歧义阻碍写作时才询问。

### 2. 梳理素材、事实与数据
区分：已确认事实、用户观点、可引用数据、待核内容和不能推断的信息。多份素材先消重、统一时间和统计口径；存在冲突时不自行裁定；按[素材整合规则](references/writing-review.md#多份素材整合)说明来源差异，并在用户定口径后同步相关结论。

### 3. 设计结构、提炼观点
确定一条中心主线，按文种组织层次。标题要准确、平行、有信息量，避免“加强力度、持续推进”式空泛小标题。简单任务不必先展示提纲。

### 4. 起草、修改、润色
段落尽量做到观点—事实/分析—措施或意义相互对应。用准确、顺畅、自然的中文；优先修正逻辑、重复、空话，再调整措辞。压缩保留关键事实，扩写不得新增虚构事实。多轮修改遵循[编辑纪律](references/writing-review.md#多轮编辑纪律)，不让已删除内容回流或无故改动已确认段落。

### 5. 审校并交付
核对主体、时间、数字、单位、口径、完成状态、政策引用、标题层级、前后逻辑、语病与保密风险。成稿任务默认直接输出最终文稿；审校任务按输出规则交付问题与建议。重要复杂稿按[读者检查](references/writing-review.md#重要复杂文稿的读者检查)核对理解障碍；短稿不增加额外流程。必要的待核事项及导出提示与正文分开。

## 五、输出规则
- 用户要成稿：优先完整正文，不附加无关前言。
- 用户要提纲：给出主线清晰、层级合理的结构。
- 用户要润色：保留原意，交付润色后的全文；用户要求时再说明改动。
- 用户要审校：按原文位置或摘句列出问题、依据和最小修改建议，区分事实/口径、逻辑问题与风格建议；按用户要求提供修订稿。
- 用户要多个版本：按场景或语气提供真正有差异的版本。
- 用户要求字数：约数尽量贴近；精确值或硬上限按[长度核验](references/summary-and-imitation.md#长度核验)实际计数，不用空话凑数或删掉关键限定来达标。
- 信息不足但可推进：明确占位并完成可写部分；不得把推测包装成事实。

## 六、DOCX 导出交接

- 先交付本次写作或审校内容，再在正文外单独问一句：“是否需要将以上内容生成 DOCX 文档导出？”提示不属于正文，不等待回答才交付内容。用户已明确只要文本、不导出或不再提示时省略。
- 只有用户确认导出，或原始请求已明确要求 DOCX，才交给本项目 `docx` Skill；已有授权时不重复询问是否导出，也不要求再次确认同一版正文。多版正文或待核事项导致导出内容不明确时，只澄清具体内容。
- 交接用户确认的最终正文及已有格式要求；若原请求已授权起草并导出，则交接按该请求完成的最终正文。排除导出提示、过程说明和用户未要求纳入的审校意见，不擅自重写事实或悄悄删除待核信息。
- 由宿主定位并读取本项目 `docx` 的真实 `SKILL.md`。仓库内入口为 `skills/docx/SKILL.md`，此路径相对于已确认的仓库根目录；独立安装时不假定相邻目录。后续环境自检、输入组织、格式选择、生成和验收遵循该技能当前说明，写作阶段不提前执行其自检。
- `docx` 不可用或其自检、生成、验收失败时，保留已交付文本并如实说明受阻；本技能不自行生成文件、不安装依赖或改用其他格式。只有生成及验收成功并核实实际文件后，才提供真实文件链接并说明已生成。
