## 银行邮件适用与核心原则

在商业银行日常运营中，电子邮件是行内跨条线沟通、分支行与总行职能部门联络、以及对接对公客户、政企单位、金融同业与境外机构最主要、最具追溯力的正式通信媒介。银行邮件要求**“开门见山、事实精准、分工清晰、时限明确、恪守保密”**。

### 邮件结构“黄金三角”法则

高效的银行工作邮件必须在打开后第一屏内完整呈现核心信息，严格遵循“黄金三角”结构：

```text
【首段·缘由背景（Why）】—— 1~2句讲清为什么写此邮件（政策依据、项目背景或前序会议）。
【中段·核心事项（What）】—— 条目化呈现核心诉求、方案要素、数据对比或附件清单。
【末段·行动请求（Action & Deadline）】—— 明确希望受件人采取的动作及反馈截止时间点。
```

### 主题行命名规范与层级标识

邮件主题应让受件人识别事项和所需动作；按受众与用途选择要素，避免只有“请查收”等无具体事项的主题。下面是可选结构，不要求每封填满：

**【重要程度/性质标识】+【机构/部门/客户名称】+【核心事项/项目全称】+【行动请求或时限】**

- *常规工作*：`【方案报审】公司金融部关于XX集团综合金融服务方案的会签请示（请于10月28日前反馈）`
- *催办与加急*：`【急件·请批复】XX支行关于XX制造业企业项目贷款用信审批的催办沟通`
- *跨条线协同*：`【需求协同】个人金融部关于手机银行8.0理财模块优化需求的沟通备忘`
- *外部客户*：`【XX银行】关于XX股份有限公司2026年银团贷款筹组进展与意向确认函`

## 常见场景结构与可选示例

常见邮件用下表与合规红线即可起草；只填写素材支持的事实，未定安排写建议/待确认，不为填满结构补造内容。

| 场景 | 最小正文结构 | 关键限定 |
|---|---|---|
| 通知、提醒、催办 | 已确认事项 → 当前状态/缺项 → 所需反馈与已定期限 | 无时点依据不补钟点，催办不暗示已获审批 |
| 会签、审批进展 | 申请与补件记录 → 待核问题 → 请求反馈进度或缺项 | 不代写批准或风险可控结论 |
| 科技、数据协作 | 问题与证据 → 需求范围 → 待评估事项与期望排期 | 期望不写成已部署或性能承诺 |
| 风险督导 | 已核信号及范围 → 核查任务 → 已授权反馈要求 | 不从单一指标直接作风险定性或处置决定 |
| 客户、政企跟进 | 会谈事实/诉求 → 已确认事项与待评估方案 → 请对方核对的行动清单 | 意向、审批、测试、上线分开 |
| 银团、同业意向 | 已授权披露的项目状态 → 待议要素 → 意向反馈 | 意向不等于参贷或承销承诺 |
| 财富服务、双语联络 | 本次沟通目的与可披露事实 → 待核问题 → 预约/确认请求 | 不预设适当性、收益或法律结论；双语事实一致 |

客户邮件仅在确需服务解释、异议/投诉处理等专业内容时追加 `<skill-root>/references/customer-communication.md`，不因收件人是客户就叠加。需要详细填写示例时才读 `<skill-root>/references/email-scenarios.md`；整文件读取的宿主也保持可选。新增或核验信贷、AML、公开舆情等业务结论时，按主入口选对应专项，邮件结构不替代专业边界。

## 邮件合规红线与保密审查

本 Skill 仅起草文本，不发送邮件、不设置收件人、不处理或加密附件。承诺与信息披露按授权、受众及适用制度核对，不提供法律效力认证。

1. **最小必要披露：** 不把密码、验证码、完整支付或身份信息加入稿件，不以证件号码片段作为密码示范。客户明细按实际用途和行内规则脱敏；某一固定掩码样式不代表充分保护。需要附件时只列应核对的内容与披露范围，未处理附件不能声称已加密、已检查或已发送；传递方式依已确认的行内安全流程填写。
2. **受众与承诺：** 收件人、抄送和回复范围由用户授权确认；无需广泛抄送，不擅自扩大传播。未批额度或优惠不得写成批准事实，必要时明确待审批状态，不靠免责声明掩盖真实承诺。
3. **声明与语言：** 保密声明采用适用的行内模板和收件人语言；无模板时不编造强制条款。普通短邮件不机械追加双语长尾。客户要求英文/双语时才提供对应版本，事实一致。

**合成短例：** 用户只要“提醒团队明天提交已安排的周报”，可以给简短事项与动作；没有附件信息就不写“附件已加密”，没有时点依据就不补具体钟点，不附无关法律声明。
