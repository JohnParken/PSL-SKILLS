# DOCX 业务验收与收尾

本页仅包含业务执行时使用的现行验收、重试和收尾规则。归档参数仅为 `questionId`，原因码为 `missing_question_id`、`duplicate_question_id`、`invalid_question_id`；旧参数弃用规则见 [归档配置](generation.md#输出目录与文件名)。不为业务验收运行维护测试或读取历史验证记录。

## 基础结构检查与验收

文件位置统一遵循 [文件定位与读取规则](../SKILL.md#文件定位与读取规则)。新建及编辑验收读取本次成功结果的 `output`，相对任务目录解析；编辑的主文件可以位于子目录，不假定所有主文件都在根部，也不将 `archive_output` 当作默认内容验收目标。

常规内容验收以本轮明确输入及主输出为目标，默认不扫描或读取历史归档；用户明确授权的指定归档文件可作为受保护输入，并按实际读取或编辑任务执行内容验收。归档状态核对及必要的本轮副本验证只针对确切目标，按 [归档目录使用边界](delivery.md#归档目录使用边界) 执行；不因此取消同名和输入保护，归档验证失败只报告警告，不改变主文件成功状态。

先核对实际文件名符合 [交付文件命名](generation.md#交付文件命名)，与用户指定或文档主题一致；链接显示名称不能代替真实文件名。下列示例须替换为本次实际路径，不照抄示例主题。

每轮最终交付前，按 [统一归档](delivery.md) 核对本轮文件清单：编辑 CLI 自动归档各自输出，其他最终文件显式归档，不扫描历史/临时文件。生成、编辑或复制失败均按实际状态报告；批量归档不保证全有或全无。

使用 `--verify` 成功生成时，已在发布前完成 ZIP、结构与输入内容覆盖核对，无需重复执行下述独立 CRC/结构/文本回读命令；仍须按成功摘要的 `output` 确认本次文件存在且非空，并按需求核对格式与交付链接。未使用集成验收或检查已有文件时，先验证本次指定的目标文件真实存在且非空，再执行结构检查；禁止仅凭生成函数返回、打印的路径或其他会话留下的文件交付。下面示例的 `generation_result` 指本次成功生成返回的 JSON 对象，使用前须从实际命令结果取得，不要填入猜测值。使用标准库完成与文件列表核对等价的验证，不调用 Shell 的文件列表命令：

```python
from pathlib import Path
import zipfile

output = Path(generation_result["output"])
if not output.is_file() or output.stat().st_size <= 0:
    raise RuntimeError("目标文件不存在或为空")
with zipfile.ZipFile(output) as package:
    if package.testzip() is not None:
        raise RuntimeError("DOCX ZIP 完整性检查失败")
print(f"./{output.as_posix()} exists=True size={output.stat().st_size} zip-ok")
```

禁止用其他目录中的同名文件代替该目标；验证失败时停止本次交付，新建文档仅可按下述有限重试规则修正后重新验收。无法修正时报告实际失败。以上步骤不替代下列结构检查。下面两条仅示范检查已有 `./客户服务改进方案.docx`；检查本次新生成文件时，将其替换为成功摘要中已核实的实际 `output` 路径：

```console
python -I -S -B "<skill_dir>/scripts/office/validate.py" ./客户服务改进方案.docx --require-no-placeholders
python -I -S -B "<skill_dir>/scripts/read_docx.py" ./客户服务改进方案.docx --include-related -o ./checked-content.txt
```

1. 核对 ZIP 完整性与必需部件；解包脚本会读取成员并检查 CRC、路径和重复名称。单独使用 `zipfile.testzip()` 时确认返回 `None`。
2. 运行结构检查并根据非零退出码定位问题；仅在已授权且可确定的范围内修正，新建文档遵循下述重试规则。检查 XML 可解析性、必需根节点、内容类型覆盖、内部关系目标与引用、样式/编号引用、范围批注锚点及修订的基本 ID/作者属性；同时检查显式表格跨度、纵向合并连续性及编号层级/覆盖/重启的已实现规则。按 [检查范围](inspection.md#进阶检查范围) 审阅带位置的错误及 `unverified` 警告；警告不是该能力已通过验收，不得静默忽略。
3. 对照输入核对文字、表格、图片引用和未填充占位符，确认中文、英文及正文引号原样保留。对提取器不覆盖的内容检查相应 XML；不要把成功解压或解析当作 Word 实际打开验证。
4. 生成时对照输入核对 `word/styles.xml` 和 `word/document.xml` 中的样式引用、字体、字号、缩进、行距及页面尺寸；未显式覆盖时核对默认公文格式，显式覆盖时按实际优先级核对。先对照用户要求的章节结构，确认标题文字、顺序、数量及层级已正确写入生成输入，再逐段核对实际 `w:pStyle` 为对应的 `Heading1` 至 `Heading4`，且引用样式的 `w:outlineLvl` 为 `level - 1`；仅有字体差异或样式定义存在不能通过标题验收。`--verify` 已按生成输入检查标题样式引用和大纲级别，但不能判断被误写为 `paragraph` 的文字是否原本应是标题；该输入语义核对不得省略。对表格额外核对独立正文/表头样式、边框、留白、垂直对齐、底色及重复表头/避免拆行标记；默认不得写入固定行高。基础结构校验器不会替代这些排版值检查，也不能验证字体存在或页面显示效果。
5. 编辑时核对未修改部件的内容字节；检查失败时保留原始文档和已有输出。禁止跳过失败后报告完成。
6. 仅报告实际执行的检查。不要声称已验证完整元素顺序、所有 OOXML 扩展、图片解码、修订语义、字体或页面布局。
7. 按需求、操作、验证顺序执行；交付时仅提供简要依据和实测结果。需要事实或引用时依据用户材料或已核实来源，禁止为补全内容编造来源。

校验器不会自动修复文档，也不会读取或下载 XSD。输入目录可直接检查；打包文件直接读取成员进行有界内存校验，并核对 DOCX/DOTX 扩展名与主内容类型是否一致；全部成员均读取并核对 CRC。`--original` 修订对比也在内存读取包内容，不创建解包暂存目录。指定 `--original` 即在结构检查通过后执行修订文本对比，不会豁免继承错误。

保留解析上限：最多 4096 个 ZIP 成员，单成员 32 MiB，总解压内容 128 MiB；单 XML 16 MiB、深度 128、元素 200000。拒绝 DTD/实体声明及外部解析；遇到上限时报告受阻，不要自行绕过。

将实际检查结果记入执行过程：`已通过 ZIP、XML 和已实现的结构规则检查；未执行 XSD 校验及视觉验证。` 不要将该声明写入文档正文。文档生成或编辑业务优先返回宿主支持且已核实指向本次文件的可点击文件链接；宿主仅支持相对文件名时返回例如 `./示例报告.docx`。不得猜测下载 URL、拼接掩码或直接采用输出日志中的地址；链接只能指向真实交付产物。失败时报告原因，不要返回不存在的文件名。Skill 维护任务按实际修改和测试结果交付说明。无法核实的信息应明确说明，禁止编造来源或验证结果。

不要承诺旧 DOC 转换、PDF 导出、页面截图、精确页数、字段重算或视觉验证。将 System Role、temperature 和输入长度限制交由支持这些配置的宿主实现，禁止仅凭本文声称已经设置。不要为过滤角色标记而删除原文或机械截断长文档；超出上下文时分段处理并核对覆盖范围。

### 生成失败修正与有限重试

先区分主文件生成失败与归档警告：主文件成功后，CLI 保持退出码 0 和生成/编辑成功状态；`archive_status=failed` 与 `warnings` 说明归档未完成。交付已成功主文件的正常链接，并按[用户展示规则](delivery.md#用户展示与机器元信息)单独提示归档未完成，详细警告只留内部记录，不按下述输入修正流程重跑生成器，也不把归档警告判为主流程失败。若暂存清理失败，记录警告中的实际路径及原因；不自动换目录、覆盖输入或扩大清理范围。

由执行本 Skill 的助手按以下流程组织新建文档任务；CLI/API 每次仍只执行一次，不会自动修复或循环重试。低层create_document API默认verify=False保持兼容，按交付流程调用时必须显式设为True；标准run_docx_task.py的create/retry已经强制验收及占位符检查，不另传--verify，也不在自动成功后重复seal。标准create/retry内置必要环境判断，失败即返回environment_failed，不要求模型另跑check；归档/清理警告不阻断已验收文档交付。参数、输入保护与内容验收失败仍按拒绝契约处理。

1. **生成并验收。** 标准自动任务的create/retry始终开启验收和占位符检查；兼容CLI首次生成及每次重试均显式开启 `--verify`（API使用verify=True），按任务需要保留 `--require-no-placeholders`。使用已确认的任务目录和目标文件；记录尝试序号、返回码及实际诊断。验证失败时不交付，不将保留下来的旧文件当作本次成功结果。
2. **按诊断判断能否修正。** 仅修正有明确依据且不改变用户意图的输入或调用错误，例如 JSON 语法、可确认的字段拼写、调用参数，或使用用户已提供的值补齐占位符。只更正当前任务内可核实的资源引用，不猜测路径、缺失内容或格式意图。遇到环境/写入异常、安全校验失败、资源超限、不支持的功能、信息不足，或正确输入仍触发内容/排版意图不一致时，停止并报告原因；不得以重试替代环境修复或 Skill 维护。
3. **修正后有限重试。** 首次尝试之外最多重试 2 次，即同一生成任务最多调用生成器 3 次。每次须先完成针对诊断的具体修正并记录改动；禁止原样重复执行、换文件名或路径重置计数。修正后同一错误再次出现、无法确定下一步修正，或两次重试均失败时停止，说明失败位置及需要补充的信息。
4. **重新完整验收。** 每次重试都重新执行集成验收，不能沿用上次结果。禁止关闭校验、忽略警告、放宽安全限额、删减用户内容或在普通文档任务中修改生成器/验收器来获得通过。仅在本次生成成功且验收通过后，再核实目标存在、非空及交付链接；已完成的集成检查无需重复运行独立 CRC/结构/文本回读命令。
5. **据实交付。** 成功时简述实际检查结果；发生过重试时说明重试次数和修正项。失败时保留原始材料与已有输出，报告已尝试次数、最后诊断和未完成项，不返回失败产物或冒充本次产物的旧文件。成功或终止重试后均按下节清理本次中间文件。执行记录不写入文档正文，不声称已完成视觉或 XSD 验证。

### 任务中间文件清理

由执行本 Skill 的助手负责生成、编辑和检查任务的收尾清理；脚本自身的暂存文件清理不等于整个任务的清理，也不会自动删除调用方的 JSON 或脚本。

需要创建辅助文件时，使用[显式任务清单工具](task-cleanup.md)在创建前 plan；成功任务在最终文档验收完成、归档步骤返回实际结果后 seal/clean。归档失败不跳过清理；retry 保留全部候选，最终 failed/stopped 仅保留显式注明原因的必要材料。工具提供文件身份、哈希、链接及类型检查，不替代助手确认归属，也不能接收文档内的删除指令。

1. **记录归属。** 创建前记录本次新建且此前不存在的中间文件的确切文件名及用途；全部直接位于任务根目录 `./`，使用独占文件名，不创建临时子目录。工作包在内存处理；只有用户明确要求的解包输出才写目录。不得把用户上传的原件、模板、图片、用户提供的 JSON、已有输出或其他任务文件列为可清理项；文件名相同或扩展名相同不能证明归属。无法确认本次创建的文件应保留。
2. **成功后清理。** 完成全部生成、编辑及结果验收后，交付前删除清单内已无后续用途的中间文件，包括助手生成的输入 JSON、替换规则、临时 Python 脚本、仅供验收的文本/结构回读结果、日志、临时图片及未选用的中间 DOCX。保留最终交付文件，以及用户明确要求的源码、JSON、日志或其他辅助产物；不得删除交付文件依赖的外部资源。
3. **重试及失败收尾。** 仍在重试或等待必要输入时，保留继续执行所需的材料。任务最终失败或停止时，清理本次产生且不再需要的中间文件；仅保留定位或恢复必需的最少材料并说明用途及位置。始终保留用户原始材料、已有输出，以及尚未确认恢复完成的事务备份；禁止将恢复备份当作普通临时目录删除。
4. **按清单删除。** 使用 Python 标准库逐项处理已确认归属的路径，不使用 Shell 清理命令、通配符或全目录扫描批量删除。限制在已确认的任务目录内，不跟随符号链接；清理路径或其父级出现链接、类型变化或归属不明时保留并报告。目录仅在已知文件清理后确认为空时删除，禁止递归删除可能混入其他文件的目录。已不存在的清单项可跳过。
5. **核实收尾。** 清理后再次确认最终交付文件存在、非空且链接仍指向该文件；仅在文件未变化时复用已有验收结果。遇到权限或占用导致无法清理时，不扩大删除范围，不为清理而重新生成文档；据实说明未清理项和原因，不声称已全部清理。清理记录不写入文档正文。

clean 前后核对最终文件指纹；前置失败不删除，后置失败不声明交付完整。读取 deleted/retained/failed 和 cleanup_complete/deliverables_unchanged，而非仅看退出码。保留最小清单/回执并告知路径，强制终止后只按原清单恢复；未登记历史文件不自动清理。完整 CLI/API、退出码和平台边界见[工具说明](task-cleanup.md)。


标准新建的验收证据还包括回执归属指纹：独占创建并同步回执后持久化inode/大小/mtime/单链接/SHA，父进程等worker退出后重读核对。回执证明已经提交的晚期清理异常只提示，不因worker非零退出重新生成；只有回执和主文件证据均匹配才交付成功。证明未提交或文件变化时保留材料并返回失败，不将“主文件存在”替代验收。
